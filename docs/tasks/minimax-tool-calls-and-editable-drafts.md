# MiniMax 工具调用与视频工作草稿改造方案

> 历史提案与当时验收边界。以下批次及开工条件已撤销，现行任务见 [I8](i8.md)。

本文为设计提案。核查日期为 2026-11-19，依据是 MiniMax 当前文档、Rookie Cut 工作区实现，以及 LegitEvi 项目的一轮实际请求。核心目标是让“给这个网站做宣传片”直接进入可恢复的创作过程。编辑中的版本允许不完整，交付以指定版本实际生成的成片为准。

## 一、协议核查

| 项目 | 核查结果 | 对应改动 |
| --- | --- | --- |
| 请求与结果配对 | 使用 OpenAI 兼容 Chat Completions，工具放在 `tools`，参数从 `function.arguments` 解析，结果用 `role: tool` 和 `tool_call_id` 返回。该事故中，主循环有后续请求可比对的 10 次调用都找到了同 ID 的一条工具结果 | 保留协议和调用 ID。解析、执行和失败反馈共用原 ID |
| 完整 assistant 消息回传 | 官方要求下一次请求带回完整 assistant 消息，保留模型实际返回的思考字段。我们的非流式实现只向上层交付清洗后的正文和解析后的工具调用；流式把思考片段仅用作活跃信号。循环随后重建 assistant 消息。第 07、09 轮的响应省略了 `content`，回传时变成空字符串，部分轮的参数字符串也被重新序列化。对照的 10 轮中，参数解码后的值一致 | 对 MiniMax 增加供应商消息的保真回传，覆盖普通请求、流式请求、重试和上下文恢复 |
| 工具调用附言 | 官方没有要求每个工具调用另有非空聊天正文。我们的 `service_per_call` 在参数检查前同时拦截空正文和批量调用。事故中第 03、07 轮各只有一个工具，原参数离线通过 Pydantic 和问卷业务校验 | 将执行条件和界面文案分开。保留有副作用的批量写入约束 |
| 模型参数 | 事故使用 `minimax-m3`、`thinking.type=disabled`、`reasoning_split=true`。当前官方文档允许 M3 关闭思考；指南示例已换为 `MiniMax-M3.1-Flash`，该型号传 `disabled` 会返回 HTTP 400。OpenAI 兼容文档说明两者的 temperature 固定为 1，本次传入的 0.2 不具备预期的调温效果 | 按实际型号生成参数和测例。修复回传与制作流程可以继续用现有型号，型号升级另行验证 |

本次有明确依据的停工链路是“强制五项偏好 → 正文检查拦截合法修参 → 普通答复仍可收尾”。这次请求关闭了思考，日志不能把停工归因于思考字段丢失。完整回传是在相同代码中另外发现的协议缺口。[MiniMax 工具调用指南](https://platform.minimax.cn/docs/guides/text-m3-function-call) · [MiniMax 的 OpenAI 兼容参数](https://platform.minimax.cn/docs/api-reference/text-openai-api) · [事故记录](../../artifacts/diagnostics/legitevi-9526efb6/RookieCut逐轮记录.md)

## 二、将校验放到真正依赖它的操作上

| 时机 | 必须成立 | 可以暂时缺失或变化 |
| --- | --- | --- |
| 接受一次操作 | 有可识别的工具、能执行的参数、正确的项目权限和目标草稿版本。重复或并发请求不能重复扣费或覆盖更新 | 用户可见附言、未指定的创作偏好、其他镜头的完成度 |
| 编辑与保存工作草稿 | 改动可原子应用并恢复。未准备的资源表示为待办或占位；实际绑定资源时验证身份和访问权限 | 空镜头、占位图、待录旁白、待对齐字幕、临时节奏。某个镜头不可预览时，仍能编辑其他镜头 |
| 调用具体依赖 | 如合成某段旁白，要有该段的文稿和所选声音；调用付费服务要满足既有支出授权。网页事实进入成片要有可追溯来源 | 整片完成度。暂缺网页证据时可先搭分镜骨架，文案中的产品事实标记待补 |
| 准备交付与导出 | 固定指定草稿版本，确认其满足用户明确的要求、引用可解析、没有交付阻断占位、时间线可编译。按适用要求检查画面与音频。渲染后核对可读取的产物、实际时长和所需音轨，再记录交付 | 用户没有明确限定的节奏和创作风格由编辑决定。交付后仍可从已有版本继续修订 |

例如编辑把口播从 4 秒改成 7 秒，允许先保存台词，让后续三个镜头暂时失去同步。系统记录受影响区间，下一步可重排镜头或缩短口播。到预览时说明哪些部分可看，到导出这个版本时才要求解开剩余错位。整片校验失败，草稿和上一版已交付产物都保留。

## 三、实施顺序

### 第一批，修复调用循环和虚假收尾

1. 在 MiniMax 客户端同时保留协议消息和供业务执行的解析结果。非流式从 `choices[0].message` 取完整消息；流式按工具索引拼回 ID、名称、原始参数片段，并合并实际存在的正文及供应商字段。清洗后的正文只供 UI，归一化后的参数只供执行。在下一次供应商请求中回放原消息，并给每个调用配一条成功或失败结果。工具参数截断或非法时，禁止执行残缺的写操作。同一上下文内重试要保住完整消息组；跨会话恢复和压缩以已完成的整组为单位，旧记录没有的字段不补造。模型私有协议字段留在供应商上下文，不进入用户聊天正文。[供应商客户端](../../apps/api/app/providers/llm/minimax.py) · [工具循环](../../apps/api/app/agents/tool_loop.py)
2. 工具消息有调用时先按该工具的执行条件处理。读操作、草稿写入、参数修复均允许无附言。问卷第一次就没有附言时，卡片标题可以独立展示。修参沿用已保存的邀请语，UI 只展示一次。同步移除 plan 和 conversation 执行器对问卷附言的重复要求。纯聊天答复仍需可展示内容。[方案阶段执行器](../../apps/api/app/chat/plan_turn.py) · [对话阶段执行器](../../apps/api/app/chat/propose_turn.py)
3. 制作回合的结束由服务端记录实际结果。已挂出问题、确有阻塞或取消、已有符合本次请求的草稿或成片，都有对应证据。“已建草稿”对应草稿写入，“渲染中”对应任务已创建，“可交付”对应产物核验。只有普通 `answer` 且制作仍可推进时，继续下一项可执行工作；确实失败时，按现有重试上限保留草稿并返回实际阻塞。普通咨询仍允许直接答复。这样即使正文措辞变化，也不会把一句承诺结算为已开工。
4. 对模型提交的 Brief 更新逐字段处理。可接受的字段由现有来源优先级合并，错误字段给出准确位置和写入结果。用户明确表达的值有原话或选项回执作依据。第 10 轮的裸数组不应导致同一更新中合法的片长和画幅一同丢失，也不能让模型替用户确认默认值。[Brief 容错](../../apps/api/app/models/schemas.py) · [已有合并逻辑](../../apps/api/app/chat/service.py)

### 第二批，让一句制作请求能产生第一版

1. 将网站五项设置从开工门槛改为可修改的创作设置。复用 `website_promo_default_brief` 对缺失字段给出工作值，把调用时机从“用户跳过整张问卷后”前移到“开始可逆编辑时”。沿用 `user-stated > inferred > default`，优先应用本次用户明确指定的值。作品语言和对话语言分别处理。设置展示为可编辑摘要，用户可以在预览后改画幅、片长或叙事方向。[默认值来源](../../apps/api/app/chat/readiness.py)
2. 联动修改 readiness、可用工具清单、阶段提示词和旧测试。官网证据齐备后，首选 `design_video(save=false)` 创建分镜草稿。有独立工作可做时继续推进。只有某个决定确实阻塞当前操作，或用户明确要求先确认时，才挂出相关问题。问卷校验按本次实际要问的字段执行，保留旧问卷已签发的选项和回答映射。现有测试明确断言品牌分析后不能看到 `design_video`，需要将该断言改为新的产品行为。[阶段筛选](../../apps/api/app/chat/turn_tools.py) · [提示词组装](../../apps/api/app/chat/prompts.py) · [当前集成断言](../../apps/api/test/core/test_website_promo_wire.py)
3. 沿用现有 `WorkingDraftUpdated`、`draft_ref`、摘要校验和恢复链路；把临时占位或待处理问题存入可恢复草稿。工作版本使用编辑器实际能显示的对象表示，待绑定图片留作占位，杜绝虚构资源 ID。修改画幅后，标记受影响镜头的构图与字幕布局待检查，沿用已取得的网页和品牌资料。断线或重入从最近成功操作恢复。[草稿写入与保存](../../apps/api/app/tools/video/design.py) · [草稿恢复](../../apps/api/app/tools/video/narration_draft.py)

### 第三批，将成片检查接到已有交付路径

区分三种用户动作：保存编辑进度、查看粗剪、交付成片。保存编辑进度可以写入未完成的草稿；粗剪可以只预览可渲染的范围并标出占位；交付固定一个版本，经全片校验、渲染和产物核查后才展示为成片。用户要求“做一支宣传片”时，第一版草稿是途中产物，默认继续到约定的交付结果；用户要求“先看分镜”则在可看的分镜处交回。沿用现有版本写入、渲染和交付事实路径。对所有导出入口应用同一套交付条件，失败返回镜头或时间范围，继续修复原草稿。[内容校验](../../apps/api/app/editing/validators.py) · [版本写入](../../apps/api/app/editing/store.py) · [渲染](../../apps/api/app/pipeline/rendering.py) · [交付事实](../../apps/api/app/pipeline/run_review.py)

## 四、上线验收

| 用例 | 通过条件 |
| --- | --- |
| 重放事故第 03、07 轮 | 需要提问的场景中，合法参数即使没有附言也能挂卡，同一邀请只展示一次 |
| 重放第 10 轮 | 准确区分合法更新和被拒字段。没有草稿或任务回执时，界面不会显示已开始制作；制作请求不会以这句普通承诺成功结束 |
| 按事故的原始用户请求走新流程 | 不回答五项设置也能拿到可恢复的分镜并继续制作。另测“先问我再做”，此时应等待决定 |
| 编辑中的临时状态 | 增加空镜头可保存，待配音可离开后恢复。草稿改竖屏后能续编，用户明确要求竖屏时，横屏版本不能以满足要求交付 |
| 工具协议回放 | 覆盖流式及非流式、空正文、多调用、失败工具、截断参数、含或不含供应商思考字段；下一轮消息与原 assistant 消息语义及协议字段一致，参数字符串和调用 ID 保真，每个 ID 有且只有一条结果 |
| 失败与并发 | 旧草稿引用不能覆盖较新的修改。重复投递不会重复生成收费资源。渲染失败保留草稿，并可修正重试；旧渲染完成时不能标记新版本已交付 |

先在录制的事故数据和可控工具上验证，再用实际部署型号小流量验证两种请求模式。灰度先看三个结果：直接制作请求取得首个草稿回执的比例与耗时、没有对应回执却报告进度的次数、通过检查并成功交付的比例。按版本观察重复收费或错误覆盖。优先在官网宣传片路线切换，可按路线撤回新路由，已生成草稿保持兼容。
