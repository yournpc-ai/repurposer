在端口 5966 的隔离 PostgreSQL 上运行 `test_project_job_deletion.py` 与 `test_export_stop_races.py`，15 项通过。每个用例使用独立临时库。409 前后逐列核对 Project、Asset、SourceSnapshot、Output、两种 Job、Conversation、Message、Wallet 与 CreditTransaction，并检查存储清理调用次数为零。两条连接分别抢先持有项目删除锁、付费准入锁，覆盖两个提交顺序。

8 积分导出用例从 100 积分开始。在准备期间 Stop，直接释放 8；在发出上传后、PUT 完成但 Output 尚未提交时 Stop，余额均保持 92，结果待核对。核清后余额回到 100，账本只有 hold 和 release，原 opening 已取消且不能唤醒。Output 先提交的对照用例余额为 92，存在唯一 Output 和一次 capture。重复 Stop 与失效 claim 重放均未改变结算。

强杀用例在独立子进程提交真实 claim 和上传身份后发送 SIGKILL。接手的 Worker 进行三次只读核对，仍无证据时进入 unknown；项目删除返回 409。之后针对同一 Job 运行显式核对入口，或由发起上传的旧执行者迟到回报已存储，均由新的有效 claim 完成清理结算。运维入口为 `python -m app.pipeline.export_jobs --reconcile-upload <job-uuid>`，无肯定证据时保留预占。

故障用例以可控制时序的 Renderer 和对象存储替身驱动。Renderer 自身另用本地 HTTP 服务实发 PUT，在丢失响应、503 和重定向三种情况下均观测到一个请求。Renderer 的 14 项测试通过。以上记录未计作 TOS 实际导出、真实付费或十用户验收。
