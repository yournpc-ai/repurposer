# Repurposer 单作品 A/B/C 渲染实验

2026-11-23 · macOS arm64 · 仅本地隔离实验

**已有证据支持继续评审 B。** 对这个 8 秒作品，去掉 Generator 中间 MP4 后，首次成片从 28.05 秒降到 16.90 秒，首次修改标题从 24.72 秒降到 16.70 秒。热缓存下优势缩小。C 的完整合成更快、峰值内存更低，但其逐帧选样、色彩转换、预览与执行隔离均增加了维护责任。单片结果不足以支持替换正式 Renderer。仅改 Impact 时，三条路线收益最大的操作都是复用已验证的视频流。

## 作品与公平条件

以只读 main 的 4d0113474101b65c9a8d9e53d47879c6e8010c91 为基线。夹具使用实际 CompositionContent、validate_content、content_digest_of、GeneratorObject.program_digest 及 compile_video_spec，在磁盘保存 CompositionVersion 的内容、父版本和身份。三条路线读取同一条版本链。没有运行数据库、Chat 或 ExportJob，没有修改 Agent Loop、主仓或正式 Renderer。

## 三条制作路线

| 路线 | 实际运行路径 | 此实验需维护的实现 |
|---|---|---|
| A | 实际 .484 bakeComponent + Seatbelt worker，运行完整 Generator 工程，输出 900×210 中间 MP4 与预览。按 program_digest 命中缓存。正式编译器验证摘要，将其编成普通视频，再由共享 Video、OffthreadVideo、Audio 与 renderMedia 输出 | 复用现役策略、动态检查、烘焙与普通媒体路径。实验 bake 适配 12 行；和 B 共享 26 行渲染驱动、11 行 Composition 入口及仓库 Video |
| B | 其他轨道走同一编译器和 Video。隔离适配器从同一 Generator 来源取出 TSX/props，将标题挂到最终 React 树的 Sequence 上方；标题内部取 clip-local frame。素材解码、音频与最终渲染仍交给同一版 Remotion | 复用现有共享画笔和播放器。新增职责是直接加载受信代码、局部时钟及资源就绪。本实验标题在最上层，无其它轨道穿插遮挡，不证明任意 z-order |
| C | 自有薄适配将同一普通轨道投影到 FFmpeg。Chromium 只画可见的 150 帧 TSX 标题，将无损 PNG 经管道送进同一次最终合成。FFmpeg 直接解码两路视频、按源 PTS 选样、叠图、混音并编码，无中间标题文件 | chromium.py 72 行、Direct.tsx 9 行、build.cjs 7 行。自行承担帧率映射、源窗、滤镜排序、音频延迟、字体等待、浏览器进程与编码错误。该路径仅实现夹具所用的固定布局、恒速 CFR、单标题及普通音轨 |

以上为物理源码行数，包含空行与注释，仅描述本夹具的维护面。共有的原创标题、素材生成、夹具校验、审计、恢复测试不计入路线差值。A/B 复用的 Video.tsx 本身有 521 行，另依赖 video-spec 和 Remotion 的媒体实现，不能把它们计作 B 新增成本。C 使用 React/DOM、esbuild、Playwright/CDP、Chromium、PyAV 读取源流频率及 imageio-ffmpeg 提供的 FFmpeg 9 二进制；无 Remotion 渲染调用。A/B 使用 .484 全家桶、React/DOM 19.2.7，以及安装锁中的 FFmpeg/compositor。B/C 只执行这次审阅的原创代码，尚无面向不受信代码的产品隔离合同。[A 烘焙](src/bake.ts) · [A/B 入口](src/RemotionRoot.tsx) · [C 合成](src/chromium.py)

## 首次制作、两次修订与重复渲染

Apple M2，8 核、16 GiB。每条路线、每个版本各运行三次，每次生成全新的成片。下表每格为同版本三次墙钟秒数，含输入摘要核对、子进程、写盘和最终时长校正。没有以成片缓存命中代替渲染。V1 第一次无该路线的 bundle 或 bake 缓存；V2 第一次是有父版缓存的真实修订；V3 第一次已有相同视觉来源。各次重新启动进程，热指复用应用级制品。未清 OS 文件缓存，未隔离其他桌面负载。主样本按 A、B、C 顺序执行，每组三次不用于估算总体 p95。

| 版本与工作量 | A（秒） | B（秒） | C（秒） |
|---|---:|---:|---:|
| V1 首次及两次复渲 | 28.05 / 16.02 / 16.11 | 16.90 / 14.70 / 14.61 | 5.15 / 4.76 / 4.77 |
| V2 标题源码、内容与参数修订 | 24.72 / 16.26 / 15.79 | 16.70 / 15.09 / 14.45 | 7.37 / 4.77 / 4.78 |
| V3 仅 Impact 修订，全片重渲 | 15.82 / 15.79 / 16.02 | 14.88 / 15.12 / 14.74 | 4.78 / 4.76 / 4.77 |
| 9 次中最高采样进程树 RSS | 2371 MiB | 2538 MiB | 807 MiB |

RSS 每约 0.2 秒采样，以父子关系汇总，可能重复计入共享页、漏掉瞬时峰值。未计独立的基准驱动与本机静态素材 HTTP 服务，原始 ps 样本未保存；每次峰值、采样数、退出码和墙钟时间已保存。原始与校正后的 9 组三次均核对文件摘要；校正后每组三份字节相同，故其完整解码结果也相同。[原始计时](logs/bench.jsonl) · [最终计时](analysis/costs.json) · [三次摘要](analysis/repeat.json)

**A→B，去掉中间烘焙。** V1 省 11.16 秒（39.8%），其中 A 的受控 bake 8.84 秒；V2 省 8.03 秒（32.5%），其中新标题 bake 8.17 秒。A 的落盘夹具编译每次新 bake 另耗约 0.66–0.67 秒，是实验适配开销。V3 首次只差 0.94 秒，因 A 已复用旧 MG。V1 热复渲中位数从 16.06 降至 14.65 秒。B 去掉了一次标题有损编码、储存与回读，未观察到峰值内存优势。B 仍需渲染整棵最终 React 树。

**B→C，去掉 Remotion 合成链。** V1 首次从 16.90 降至 5.15 秒，省 11.74 秒（69.5%）；V3 全片重渲首次从 14.88 降至 4.78 秒。C 只送标题小区域给浏览器，视频和音频在 FFmpeg 中直接合成，因此观察值包含工作划分带来的收益。缺少完整原生对象、编辑播放器和生产隔离的实现成本，不能折算成“等能力全面替代”的净收益。

**同编码器复核。** 在 V3、热来源、进程重新启动的情况下，交错执行 BC / CB / BC。强制 B/C 最终编码都使用同一本机 FFmpeg 9、同版 libx264、2 个编码线程、veryfast、CRF 18、AAC 192 kb/s；用 MP4 的 muxer 标记和 H.264 SEI 核对，原 B 为 core 165 / 12 threads，对照两路为 core 164 / 2 threads。B 为 15.47 / 15.70 / 15.50 秒，C 为 7.60 / 4.78 / 7.60 秒；中位数节省 **7.91 秒（51.0%）**，采样峰值约 2238 对 787 MiB。此组测直接渲染，不含主表的交付校正，公共编码器控制了一个重要变量；剩余差异仍含解码器、栅格面积、像素传递、混音和调度。没有用 A→C 差值估算去 Remotion 收益。[对照命令与运行](src/encoder_control.py) · [成片内的编码器证据](analysis/encoder-control.json)

**独立成本。** 重新生成共享原始素材并逐一核对字节，主视频、PiP、语音合成/转换、Whoosh、首版 Impact 合计约 2.63 秒；该一次性公共开销可分别加到 V1，不重复计入每版。V3 新 Impact 的配方合成约 0.9 毫秒。额外实测在 V2→V3 先比对完整视觉投影，再复用 V2 视频流，仅重混三轨音频并封装：A 0.178 秒、B 0.161 秒、C 0.150 秒。每种结果的 H.264 包载荷摘要均与该路线完整 V3 相同。该优化控制使用同一 PCM 混合与 AAC 编码，音频同参考混音相关约 0.9914，不保证与各路线完整 V3 的 AAC 字节相同。没有外部生成/导出订单、数据库扣费或实测云端单价；以上是设备时间、内存与重新制作次数，不能据此给出货币报价。[素材复产计时](logs/shared-material-cost.json) · [声音局部修订证据](analysis/local-audio-edit.json)

## 画面、时钟与声音核验

**帧与 PTS。** 三条路线各三个版本的代表文件均全片解码。输出从 0 到 239，每帧 PTS 精确为 k/30，结束于 8 秒，修正后容器、音轨也均为 8 秒。把每一源帧的像素编号还原，与源容器实际解码 PTS 比较。按“取最近源 PTS，等距取后帧”的参照，主视频三路均 240/240；PiP 可见的 195 帧中，C 为 195/195，A/B 为 192/195。在输出帧 72、126、156，A/B 取前帧，C 取后帧，距离均为 20 ms。三路都没有选择比最近帧更远的帧，亦没有逐渐累积的漂移。若指定“只取时间戳不晚于目标的帧”，结果会不同；两种判据都逐行保留。[逐帧 PTS、实取编号与偏差](analysis/source-pts.csv)

**画质。** V3 完整 240 帧 RGB 比较，A/B 平均绝对差 0.267/255、PSNR 47.31 dB；标题框内平均差 1.226，框外 0.171。B/C 平均绝对差 2.323/255、PSNR 38.56 dB；标题框内 1.249，框外 2.431。C 的差异分布在素材区域，存在不同选样、缩放、解码、色彩转换与编码路径，尚未逐项分离。V2 和 V3 在各自路线内解码画面完全相同；V1 与 V2 的音频在各自路线内完全相同。这里的 PSNR 衡量两路差异，不能据此断言某一路是视觉真值。[逐帧误差](analysis/frame-errors.csv) · [各版本解码摘要和闪光帧](analysis/video.json) · [三路同一帧 PNG](analysis)

**音画同步与削波。** 以三条原始 WAV、声明源窗、增益和采样位置独立产生 384,000 个立体声参考采样。A/B 原始输出音频为 386,048 采样、容器 8.042667 秒；互相关确认整轨延后 2,048 采样（42.667 ms）。保留原件，以双输入 stream copy 调整音频起点并裁 8 秒，视频和音频均无二次编码。C 原始输出即满足时长。修正后九个代表文件与参考的全轨滞后、扣除其他参考声部后测得的 Impact 滞后均为 0 采样。三路闪光均在第 60–62 帧，Impact 在第 60 帧对应的采样 96,000 开始。结论来自解码字节，不依赖播放器进度条。[原始输出](results) · [逐次校正命令](logs/conform.json)

在 2.0–2.6 秒重叠窗口，旁白、Whoosh、Impact 三个参考声部均有能量；三声部回归系数均非零。V3 中旁白/Impact 的系数接近 1，高频噪声 Whoosh 在 A/B 约 0.50、C 约 0.59；AAC 编码后的 Whoosh 无法按原 PCM 波形完全重建。V3 参考相关系数 A/B 0.9892、C 0.9915，A/B 的解码 PCM 摘要相同。所有版本实测削波采样数为 0，true peak 在 −7.9 至 −7.7 dBTP。没有独立盲听评分。[解码 A](analysis/decoded-A.wav) · [解码 B](analysis/decoded-B.wav) · [解码 C](analysis/decoded-C.wav) · [混音参考](analysis/reference-v3.wav) · [音频统计](analysis/audio.json)

## 预览、中断与已知失败

- **渲染预览。** A/B 独立调用 renderStill，C 独立执行同一源窗与 FFmpeg 叠层图生成第 60 帧。三路预览均读到主视频 60、PiP 48，与各自 MP4 对齐。相对该路有损 MP4 的同帧 MAE 分别为 1.138、1.177、0.806。C 验证了定位出帧，没有实现独立交互式音视频播放器。
- **实际浏览器。** 对 A/B 挂载现有 @remotion/player，在第 45、60、100 帧 seek。首次 HTTP 服务没有 Range 支持，UI 的目标帧已更新，媒体 currentTime 却仍为 0。保存首错，给隔离素材服务增加 206/Content-Range，并等待媒体时间到位后复测。第 60 帧 Player 的源时间正确到达 2.5 / 1.9 秒，像素编号为 59 / 47，离线输出为 60 / 48。三处检查均保留实际画面和偏差；浏览器可播性通过，逐源帧一致性未通过。[首次失败](logs/failed-player) · [复测媒体时间与字体](logs/player.jsonl) · [预览与 MP4 量化比较](analysis/preview.json)
- **真实中断，局部恢复。** 每路 V3 都启动一次实际渲染，在 2.8 秒后终止进程及其当时的后代，退出码 −9，无已发布回执。重新核验版本、固定资源、实现、浏览器和运行环境身份后，以同键重渲一次。第二个子进程封存正确媒体摘要后，模拟发布前退出，退出码 73；依据 sealed 回执、身份和字节重新发布，新增渲染数 0。恢复成片均与该路不中断的最终 V3 SHA-256 一致。这里测试进程崩溃、文件级恢复与明确的两处边界，未测断电持久性、多租户授权、分布式竞争或账本。[恢复记录](analysis/recovery.json) · [每路运行原始记录](recovery/two-boundaries)
- **同编码器对照的首错。** FFmpeg 9 拒绝 Remotion .484 的旧 filter_script:a 参数。保留退出码 8 和完整子命令，在对照包装层映射到新拼写及可用 AAC 编码器后重跑。主 A/B 继续使用其原锁。Player 复测中可见浏览器提前结束 Range 请求的 BrokenPipe 日志；最终 seek 验证另以当前时间和像素证据判断。验证进程同时导入 PyAV/OpenCV 有 macOS 重复 AVFoundation 类警告；计时的正式制作进程未依赖此组合。[原始失败](logs/encoder-control-failure) · [验证日志](logs/verify.log)

## 复现与评审边界

运行命令为 `bash commands/reproduce.sh`。脚本新建独立临时目录，复制固定输入、使用锁定 Node 依赖和现有 Python 环境，重新构造作品和全部渲染；同机可直接复用现有 node_modules，离开此目录则按锁安装。基线仓库与已验证的 Mac 浏览器、系统字体路径见 env.sh 及 manifest。外部环境需要先提供同版本仓库和运行依赖。字体和系统 Samantha 语音依赖 macOS，本地包携带固定旁白 WAV。完整源码包含所有实验适配器、共享 Video/video-spec 的隔离副本及测试；正式 Python 编译器、受控 worker 与其第三方依赖按仓库提交和锁定位。[复现命令](commands/reproduce.sh) · [素材再生产](commands/make-materials.sh) · [源码](src) · [原始日志](logs) · [摘要清单](SHA256SUMS)

**架构判断。** B 的收益在首次生成和改变 MG 来源时最清楚，可以沿用既有作品与播放器继续研究受信来源的直接合成。A 具有可独立缓存的固定媒体和受控执行边界，仍是未经信任来源的重要参照。C 在这个上层小面积 MG、两路恒速视频的样本上确有整条路线的时间和内存收益；复杂透明层、多标题穿插、旋转动画、VFR/长 GOP、HDR、跨机字体、正式部署隔离及真实交互播放尚无等价证据。三路最先暴露的共同产品问题是如何明确定义源帧选择、检验实际声音起点、让预览和交付可核对。本轮停在隔离验证。
