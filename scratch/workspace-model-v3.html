Workspace 空间模型合同 v4.2 — 最终封板版

核心原则：Graph ≠ 所有产品语义的空间化。Graph 只装值得在空间里长期存在、可以被再次指认、可以被独立操作的持久 Product Entity；Chat 承担瞬时决策、候选、预览、解释与自然语言。判定 = Eligibility（资格五问）+ Promotion（晋升）。

v4.2 收口（2026-09-26 最终封板）：① T2 事实校正——删「点开试听」（当前代码无此能力；封板文档禁止出现代码没有的交互），候选 = 时间段 + 内容摘要 + ordinal 指认；② 语言分层立法——合同/注释可用技术语言，模拟 chat prose 必须是自然人话，永不向用户解释 Graph / Canvas / Promotion /「不占画布」等内部概念；③ 命名三层——内部实现 Canvas / 产品概念 Workspace / 用户话术「工作空间」，用户侧永不听到「画布」；④ T6 空间模型修正——旧 Work 保留 + 伴侣文档向右长 + 新独立作品生成新 Work node（不是全压进 pager）；⑤ Revision ≠ New Work 立法——改同一作品的内容/参数 → 同 identity 新 version；「再做一个不同的」→ Promotion 新 Work entity；⑥ T6 更名「持续创作」（既修已有作品，也可产生新作品）；⑦ 指认措辞放宽——「具备再次指认和独立操作的价值与可能」，不承诺每个实体必然被再指认；⑧ 终态示意图改为分支增长模型；⑨ 工作空间/Graph 关系自然化——工作空间 = Agent 与用户共同工作的持续空间，Graph = 它背后的持久结构；⑩ 字幕拍按代码实况修正——修订也有「理解正文 + dock 确认行」（scope classifier 判 expansion → 回滚落 dock），字幕 = 两站三节点链（高光 → 字幕文档 → 字幕版装配节点），原高光一帧不动；⑪ 确认行按 ADR-092 三档偏好门控（always / large 过阈值 / never——不落拍时直接执行 + 正文诚实报开工估价，门控在 server 侧）；所有收尾句与普通正文同一组件，无独立消息类型；⑫ 冻结前文字级修正——C2 删净「不占空间/不需要清理」旧话术、授权门重新定义（server-side policy gate，策略直执 ≠ 无授权）、Provisional→Settled 边界钉死（付费授权边界 = settle 时刻，失败/重试不删 Work）、Revision vs New Work 反例入图。不再新增任何交互原语。v4.2 = 冻结基线，此后按差距实现，不再重开产品概念讨论。

C1

Graph Node Eligibility — 资格，不是分类

一个对象进入 Graph，当且仅当同时满足五条：

  • ① 稳定存在——不是一次性消息材料，而是被赋予稳定 Product Identity、具有明确生命周期、可跨消息持续存在的实体（Draft Work 因此合法：它有身份和生命周期，即使最终未被确认）
  • ② 独立身份——它是「一个东西」，不是别的东西的属性
  • ③ 可再次指认——用户以后会说「那个」「@它」
  • ④ 可独立操作 / 查看——点开、播放、下载、修订
  • ⑤ 值得占据空间——它在场让工作世界更清楚，而不是更吵

C2

两种 Graph Birth — Entity Birth ≠ Promotion

createGraphNode() 和 promoteToGraph() 永远不是同一个概念
  • Entity Birth（系统生命周期）：Source 上传即产生、Transcript 上传即落 queued 卡——由系统生命周期直接创建的持久实体，不属于 Promotion
  • Promotion（晋升）：「临时对象 → 持久 Product Entity」的唯一晋升入口——Candidate / 预览 / chat 建议要获得 Graph 身份，只有这一条路
  • Chat decision ≠ Promotion：「第二个不错」「第一个和第三个」「都做」「把第二个换掉」都是 chat 内决策——改变的是候选面上的选择态与接下来计划的内容，不产生任何 Graph 节点
  • Candidate → Draft Work：用户决定真正制作（「切个高光看看」并收敛为计划）→ draft work 节点出生。Draft 是计划的可视化，出生不等授权；授权拍（确认生成）只翻转状态（draft → running → ready），零生长。未被选中的候选仅作为本轮对话中的临时呈现，不转化为持久 Product Entity
  • 预览 → Work：chat 里展示的分镜/效果预览，只有用户明确采用（「就按这个分镜做」）才晋升；「看看」「不错」只是讨论。未采用的预览仅作为本轮对话中的临时呈现，不转化为持久 Product Entity
  • Promotion 永远附带一次用户或 Agent 的明确承诺，Graph 从不因「Agent 想了想」而生长
  • Revision ≠ New Work ≠ New Product：三种结局分治——① 改同一产物的参数/内容 → 同一 identity，新 version（「中文在上英文在下」→ v1→v2；「开头加 2 秒标题」→ v2→v3）；② 产出新的持久产物（「字幕也加上吧」→ 字幕版装配节点 + 字幕文档伴侣，两站 doc_node_id 链）→ 新节点出生，原 Work 原样保留；③ 用户表达「再做一个不同的作品 / 另一个独立版本」（「再做一个更快节奏的版本」）→ Promotion 产生新 Work entity（Work B v1）。Workspace 是 append-only 的持续空间——旧节点保留、新产物/新作品向右生长，不是把所有未来作品都压进一个 pager

Settled ≠ Provisional（消失纪律的分层 + 边界钉死）：

  • Settled Entity append-only：已 settle 的实体只长不消，不因后续对话自动消失——它是 Graph history
  • Provisional → Settled 的边界 = 付费执行授权边界：Draft 在跨过授权门（确认拍或策略直执）进入 running 的那一刻结束 provisional 状态；Work identity 自此成为 settled history——后续失败、重试或版本演进均不删除该 Work。「渲染失败了能不能把这个节点删掉？」——不能：节点在、状态失败/可重试，历史不擦除
  • Provisional Draft 可被重规划、替换或丢弃：未跨授权门的 draft（re-dock 让位、用户说「不要了」）不是 settled history 的撤回——它从来就没有 settle 过。「用户说不要这个 draft 了，能不能删节点？」——能，因为它还不是 Graph 的持久成员

C4

Evidence 锚链 + Transcript 双层 — 不变量

Candidate 的证据定义（住 Candidate Surface，不进 Graph）：

  • Candidate = source asset + source range + source-faithful excerpt
  • source range = 时间根（单一连续闭区间）；words / ASR = evidence truth（唯一时间权威）；excerpt = 展示事实（逐字核验，不渲染）；clip 消费 source range（秒数），永不消费 excerpt

Transcript 双层：Source Transcript（immutable：原始 ASR + meta["words"] + speaker 证据，永不改）/ Editable Transcript（presentation：用户可改的文字层，卡面直改 / 叫 Agent 改同一个写口，按位置覆盖显示，不反算、不移动任何 range）。

不变量：

  • 用户改 Transcript 文字：text changed / evidence unchanged / range unchanged——任何代码路径都不从文字反算时间码
  • Candidate discovery 默认基于 source evidence；用户改写的 transcript 不被当成新的语音事实。若用户明确要求基于 Editable Transcript 进行语义检索，允许把它作为检索输入——但任何候选的时间与媒体事实仍必须回锚 source evidence（excerpt 逐字核验、range 定位只认 words）
  • 可编辑性不是「编辑模式」：对象本身可编辑。Chat 可以自然说「你也可以直接在工作空间里改文字，或者告诉我怎么改」——一句提示，不是一个模式

Camera = ensure-in-view，全部合同就这一条

  • 规则全文：当前操作对象是否处于扣除 Chat Dock 后的 safe viewport？已在：不动。不在：最小 pan 带进可读区。zoom：永不自动改变。其他对象：不因此次操作而 dim。
  • 删除整组 focus 族：主作品聚焦 / 邻近退后 / focus 三态 / focus ring 作为产品状态——全部不存在
  • 唯一自动节拍 = Workspace Birth 的 initial fit。此后一律 ensure-in-view——包括 draft / 新节点诞生：出生点已在安全区则不动，不在则最小 pan。Canvas 是持续存在的空间，Agent 放好东西不该重排用户的空间记忆
  • 「draft 到达 → 整链 fitNow」不入合同：它曾是候选特例，未经实测证明 UX 价值前不得复活；背景 refetch 永不动相机
C6

Group Layout Island — 组内自治，零 UI

  • 每个 sibling group 出生时获得自己的 layout island：一块独占布局区域，宽度按该组的设计容量预留，不是按当前成员数
  • 岛零 UI：岛是数据结构与布局律——节点上的 group 归属 + 容量参数 + 一条摆位规则。画布上永远没有「岛」的框、标签或任何 chrome；用户只看见节点之间排得整齐
  • 组内成员从上往下排，到容量 C 换组内第二列——岛内的事；岛外永远不知道、永不让位
  • Bounding contract（「永不让位」的数学保证）：graph depth = 逻辑关系；island = 局部打包域。岛的 origin 与 size 在 group 出生即定格——宽度含全部预留列（增长廊道），成员扩列只在预留廊道内发生；深度带距 = 各带岛定格宽 + gap。任何岛的右缘永不越过出生定格的右缘 → 后续 depth 带 / 兄弟 group 的区域在数学上不可能被侵占，overlap 结构性不可能
  • 真超容量（成员数 > 预留列 × C）走集合态（contact sheet），不破廊道——扩容廊道本身若要改，是新 group 的事，不是既有岛的事
  • 一节点多 outputs（pager）是零扇出基线；sibling 同列叠放只在第二次 promotion 时才出现
C7

Motion 三语义 — 固定，不再叠加第四种

语义说的话形态
edge arrival「关系刚建立」incoming edge draw-on，一次性
node birth「对象刚出生」scale/fade-in，一次性，出生即结束
node working「对象还在工作」卡内 loading / wipe，持续到完工

禁止再叠加任何 aura / attention / focus 状态——用户不读文字也该分得清：线在长 = 关系来了；卡在长 = 对象来了；卡里在动 = 还在做。

C8

语气 — ordinal 是地址；确认拍 = 用户气泡；chat 决策永不成节点

  • 编号是视觉地址：「第二个」「第一个和第三个」「都做」「把第二个换掉」都是合法 chat 决策，系统解出目标；Agent 回复「可以，我换」——永不「好的，我现在正在处理第 2 个候选」
  • Candidate Surface 默认只露 3 个推荐 + 全量可展开——推荐样本，不是只能选 3 个
  • 确认拍归档 = 普通用户气泡：dock 的「开始生成」pill 点击等同帮用户输入「确认生成」四个字——消息流里就是一条用户气泡 + agent 开工散文，永不归档为 QA 问/答块（QA 块只服务真正的问答）
  • 授权门（Confirmation policy gate）：付费执行必须经过 server-side scope / confirmation policy gate。在需要确认的策略下（always，或 large 且估价高端过 billing.confirm_large_threshold），用户确认是授权拍（dock 确认行 → 用户气泡「确认生成」）；在 never 或未过阈值时，可直接执行，但仍必须向用户披露执行范围与估价（不询问 ≠ 不披露，世界自证律）。门控决策在 server 侧（scope classifier / plan dock 落点读 users.settings.confirm_strategy），付费边界永不交给客户端状态。代码现状：该偏好今天只调披露强度（dock 恒弹），行为接线是后续批——本合同把它立为目标语义
  • Chat 是自然语言编排 / 意图入口，不是唯一修改入口：Work 可由 Chat 修订；Transcript / 字幕文档等具有直接编辑语义的实体也可在 Canvas 直改。两个入口改的是同一个实体身份，产生的都是版本演进，永不创建新 Work
  • 语言分层（模拟 chat prose 的硬律）：合同 / 注释 / notes 可以用技术语言（Graph、Promotion、Product Entity、append-only）；模拟真实 Chat 的 prose 必须是自然、人性化的 Agent 话术——永不向用户解释 Graph / Canvas / Promotion 等内部概念，永不说「不占画布 / 不需要清理 / 不占空间」。说「先看看不同方向，喜欢哪种告诉我，我再按那个继续做」，不说「未采用的预览不会成为持久实体」
  • 封板文档事实律：模拟 chat 里出现的任何交互，必须是当前代码真实支持的能力；没有的能力（如候选试听）不得出现——未来能力落地后再补进文档

封板

五个问题，五个答案 — 不再新增交互原语

① 工作空间什么时候第一次出现？
T1——Agent 开始建立工作世界的时刻（今天是 transcript processing 实体出生的那一帧）。T0 上传 Source 时仍是纯 Chat world。Birth 是独立 presentation 谓词 workspaceBorn，与「graph entity 已存在」（数据事实，上传即始，不改）和「PLAN_READY」（lifecycle 投影，不动）三事实分离。

② 什么东西有资格成为 Graph node？
过 Eligibility 五问（稳定存在 / 独立身份 / 可再指认 / 可独立操作 / 值得占空间）的持久 Product Entity：Source、Transcript、Draft Work / Work、伴侣文档（字幕文档，上限：对用户有独立身份与独立查看/编辑/引用能力，纯装配中间产物永不入图）；Version 住 Work pager。入图两途互不冒充：系统生命周期 Entity Birth（Source / Transcript）与 Promotion（临时对象 → 持久实体的唯一晋升口）。Candidate 旧模型（Judgment / Candidate Set / 已选节点）代码级删除。

③ 什么东西只存在于 Chat / temporary surface？
候选与选择态（Candidate Surface）、分镜/效果预览、能力问答、世界模型事实、确认拍（用户气泡）、活动行、计划散文——一切瞬时决策与过程。分镜预览未经明确采用永不晋升。

④ 同一对象如何随 Chat 持续被修改，而不是被重新创建？
Revision ≠ New Work：修改已有 Work 的定义/内容/参数 → 同一 identity 新 version（pager v1→v4 原地演进，伴侣文档原地更新）；「再做一个不同的作品」→ Promotion 产生新 Work entity，向右/下一逻辑 depth 生长——Workspace 是 append-only 持续空间，不是把所有未来作品压进一个 pager。Chat 是自然语言编排入口，不是唯一修改入口：具有直接编辑语义的实体（Transcript / 字幕文档）可在 Canvas 直改；两个入口改的是同一实体身份，产生的都是版本演进。Transcript 编辑不变量：text changed / evidence unchanged / range unchanged；candidate discovery 默认基于 source evidence，用户点名时可借 Editable Transcript 检索，但时间与媒体事实永远回锚 source evidence。

⑤ 一个完整真实 Session 结束后，Graph 像不像一个越来越完整的工作空间？
像。终态 = Source → Transcript → 高光（v1 原样保留）→ 字幕文档 → 高光·中英字幕（v1–v3 住 pager）：5 nodes，主干细短、每件可再指认、有版本记忆；12 轮会话里发生过的候选、预览、事实、问答全部留在 Chat。Settled 实体只长不消，provisional draft 可弃——图长得极少、极准，是 workspace，不是 workflow diagram。

封板一句话：工作空间是 Agent 与用户共同工作的持续空间，Graph 是这个空间背后的持久结构。Graph 只记录用户未来仍值得再次指认和独立操作的 Product Entity；Chat 可以承载大量不会进入 Graph 的临时候选、决策、预览与上下文；只有真正需要持久身份的对象才进入 Graph。工作空间在 Agent 开始建立工作世界时出现，随 Product Entity 的实际产生而增长；后续对话优先修改既有实体，而不是制造新实体。

Source │ Transcript │ ├──────→ High-light A（v1，原样保留） │ │ │ └→ Subtitle Document（文档站，可独立编辑） │ │ │ └→ High-light A·中英字幕版（装配站）── v1 → v2 → v3 │ └──────→ High-light B ── v1 （「再做一个更快节奏的版本」→ New Work，不是版本）

两个钉死的判例：「中文在上、英文在下」→ 字幕版 v1 → v2（同 identity 内容演进）；「再做一个更快节奏的版本」→ High-light B v1（新 Work entity）——看到「再做一个…」不得条件反射塞 pager。旧 Work 保留、伴侣向右长、新作品继续长——示意图只表达增长形态，具体 edge 永远遵循真实 Graph relation，不为视觉强行造边。而不是「Agent 做过什么 → 全部画出来」。这就是我们一直在找的 workspace，而不是 workflow diagram。
